# kb v1.3.0

v1.3.0 gives every task a project. Exactly one `project::<name>` scoped label
per task, held by every surface that writes one: the CLI, the TUI, `kb mcp`,
and the forge import. A project slices one board rather than splitting it into
several - the deliberate opposite of the per-user namespaces removed in
v1.2.0. The schema, the wire format, and `kb serve` are unchanged; a project
is a label, and it is filtered like any other label.

## Projects

- **`kb project`** - `use <name>` sets the active project, `current` prints
  what commands default to (`--json` also names the source), and `list` shows
  every project with its task count and marks the active one (`--json` too).
- **Resolution order** - `-p`/`--project` beats `KB_PROJECT`, which beats the
  project stored by `kb project use`. The stored choice lives in `state.json`
  in the data directory, beside `kb.db`, written atomically. It is client
  state: it resolves the same way in `KB_SERVER` mode, where no local database
  is ever opened, and it never travels to the board's readers.
- **Mandatory `kb add`** - kb refuses to invent a project. With nothing
  resolved, `add` errors and names both fixes: `kb project use <name>` or
  `-p <name>`.
- **The invariant** - no task-mutating path leaves a task with zero or two
  `project::` labels. `--tag` replaces the plain labels but keeps the task in
  its project, `-p` moves it, and spelling `--tag project::<name>` does the
  same. Two of them, or one contradicting an explicit `-p`, is refused. `-p`
  alone is a complete `update`.
- **Validation** - a project name validates like any label value (non-empty,
  no whitespace, no leading `#`) plus a rejection of `::`, so a name cannot
  smuggle a second scope into the label.

## Backfill

Tasks created before projects existed are given `project::inbox` the first
time kb opens the local database. It runs on local store open - the one
startup path every local surface shares - rather than behind a command a user
may never run, because the mandatory rule is only true if it already holds for
the tasks that predate it. `kb mcp` opens its own store and runs the same
pass. The pass gives an unprojected task `project::inbox`, collapses a task
carrying several to the first, is idempotent, and writes nothing once the
board is clean.

## TUI

- **Switcher** - `p` and `P` cycle the board's scope through `all` and every
  project on the board. The toolbar carries a `[project: <name>]` segment at
  the end of the filter-field row, in the brand hue while scoped and clickable
  to cycle forward. The scope persists in the per-board preferences and the
  board opens on the project the CLI would default to when nothing is stored.
- **Filter** - the project scope runs first and the text and label filter
  narrows what it left; the toolbar count reads `N of M` within the project.
  `project::` labels are kept out of the filter chips: the switcher owns that
  axis, and a chip beside it could contradict it.
- **Card pill** - the project pill leads the label row. The row renders in
  survival order, so leading with it is what keeps a card's scope on screen
  when the row runs out of width.
- **Editor** - a mandatory `Project` field sits between Blocked and Labels,
  defaulted to the switcher's selection and pre-filled from the card's own
  project when editing. Save is refused when it is empty or invalid. A
  `project::` label typed into the Labels field, or returned by an AI draft,
  moves the card instead of stacking a second one.

## MCP and import

- `add_task` and `update_task` take an optional `project` argument that
  resolves like the CLI's `-p`. `add_task` refuses when nothing resolves, with
  the CLI's wording. `update_task` holds the invariant across an update the
  way the CLI does. `move_task` and `delete_task` write no labels, so they
  cannot drop the project.
- The TUI's forge import and ADR split stamp the active project on every card
  they create, resolved per card - so a `kb project use` during a long batch
  applies to the remainder. A board where nothing resolves fails the row with
  the same refusal instead of writing a projectless card.

## Upgrade from v1.2.0

No database migration is required. The project is a label; the schema, the
`kb serve` HTTP API, and the storage keys are unchanged. Existing tasks,
comments, links, tombstones, settings, encrypted credentials, and import
provenance remain in the same data directory. Keep `kb.db`, `kb.db-wal`,
`kb.db-shm`, and `secret` together when backing up or moving a board.

The backfill is automatic and idempotent: the first local open of an existing
database files every task under `project::inbox`, and later opens write
nothing. There is nothing to run and nothing to undo.

Existing workflows need one thing, once: name a project.

```sh
kb project use inbox   # or any name you prefer
```

After that every command defaults to it. `KB_PROJECT` sets it per shell and
`-p <name>` sets it per command; any of the three satisfies `kb add`. Without
one, `kb add` errors instead of guessing.

Scripts that pin exact tag sets should account for the project label, and
`kb list --tag project::<name>` filters by it.

## Install and verify

With Go 1.25.8 or newer:

```sh
go install github.com/RandomCodeSpace/kb@v1.3.0
kb version
```

The release contains five CGO-free binaries:

- Linux amd64 and arm64
- macOS amd64 and arm64
- Windows amd64

Download the matching binary and `SHA256SUMS` from the release, then verify it
before installation:

```sh
grep ' kb-linux-amd64$' SHA256SUMS | sha256sum -c -
```

Substitute the downloaded asset name. On macOS, pipe the matching manifest
line to `shasum -a 256 -c -`. On Windows, compare
`Get-FileHash -Algorithm SHA256` with the matching manifest line.

Every attached binary is built from the annotated v1.3.0 tag with `-trimpath`
and stripped debug data. Embedded Go metadata records the module, version,
source revision, target OS and architecture, and an unmodified source tree.
